## 0. 一句话结论（建议稿）

> **本地化的 AI 短剧「前期生产 + 交付打包」平台**：把一本小说/一段原文，做成**能被专业剪辑直接接手的一集素材包**（成片 + 分片 + 字幕 + 时间线交换文件 + 清单）。
> **图像 / 视频 / 音频必须跑本地**（16GB GPU，串行）；**文本与提示词改写可以用云端 LLM** —— **2026-10-05 已拍板（D13）**：默认走云端，**本地模型保留给特殊场景**（离线、隐私敏感、降本）；**精剪（卡点/多轨/调色）永远交剪映/达芬奇**。
>
> **已拍板（2026-10-05）**：P1 文本可上云（D13）｜P9 **画布要接入服务端事实链**（D14，关系重大，本方案 §5.5 给出三种接入深度供更高维度评审）｜P3 术语统一（阶段/跑批/模板/画布）｜P8 口径统一（段数=七段、模板=19）。
> **本轮已确认 P4**：60～90 秒完整验证短片 + 剪辑交接包；声音默认独立 TTS + 后期混音，口型同步为可选增强。**仍待拍板**：P2 四页唯一职责表｜P5 是否补 Agent 流水线工具｜P6 外部 API 口径｜P7 BR 草稿 A–F 的正式结论，以及试片质量和目标剪辑工具。

三层程度（与 BR §6 三期路线对齐，但明确"本期只锁一件事"）：

| 层 | 做到什么程度 | 判定标准（可复算） |
| --- | --- | --- |
| **现阶段（本期）** | **60～90 秒完整验证短片 + 剪辑交接包** | 贯通故事至成片，交付成片、分段视频、采用关键帧、SRT、FCPXML/EDL、清单和导入说明；完整标准见 `prd.md` §1.1～§1.4，质量与目标软件仍待确认 |
| **下一阶段** | 质量与可调整 | 统一 QC（连续性/声画/响度/黑帧）、字级字幕（FunASR）、角色造型室（可确认/可复用）、音效与 BGM |
| **未来** | 包装与规模化 | 片头/文字动效、分支重跑（回马枪）、数字人（可选）、本地化发布、P2 复用清理 |

**P4 当前口径**：首版交付剪辑交接包，在原草稿的成片、分段视频、SRT、FCPXML/EDL、清单和说明基础上包含采用的关键帧。用户已确认先用 60～90 秒试片验证完整流程；包内素材完整性、文字准确及真实导入能力不能以“zip 能生成”替代。具体质量标准和目标软件继续逐项确认（`prd.md` §1.4）。

**现阶段明确不做**：站内时间线编辑器、把编排搬进网页、模型市场、多人协作、云端生成后端（RunningHub 保留但不投入）。现阶段保留人工门禁，后期允许自动推进。声音默认采用独立 TTS + 后期混音；H3 原生音频与口型同步属于按镜头启用的可选增强。

## 2. 现状事实（一手核对，2026-10-05）

### 2.1 四条执行链路的物理位置（**这是很多误解的根源**）

| 链路 | 实际跑在哪 | 证据 |
| --- | --- | --- |
| **文本**：剧本 / 分镜 / 服化道 / 定妆身份卡 / 提示词改写 | ⚠️ **云端 DeepSeek**（`deepseek::deepseek-v4-pro` → `https://api.deepseek.com`） | `config.llm.defaultModel='deepseek::deepseek-v4-pro'`、`config.pipeline.llmModel=''`；`index.js:88` 用 `options.model \|\| pipeline.llmModel \|\| llm.defaultModel` 兜底注入；`providers/llm.js:75/243-253` 按「渠道名::模型名」路由到外部渠道；实测渠道表 `deepseek → https://api.deepseek.com`（`GET /api/llm/providers`） |
| **图像**：关键帧 / 角色参考图 / 场景母版 / 换装 / 放大 | ✅ 本地 ComfyUI（147 机器） | 文生图 4 + 编辑 3 + 放大 1 个模板；`config.generation.defaultBackend="local"` |
| **视频**：片段 / 对口型 | ✅ 本地 ComfyUI | 视频 8 + 对口型 2 个模板；GPU 队列并发 1 |
| **音频**：TTS | ✅ 本地 147（`audio_qwen3_tts`，音色库只读探测） | `voices.js` + `GET /api/tts/voices` |
| **成片 / 字幕 / 拼接 / 打包** | ✅ 网关 CPU + ffmpeg | `delivery.js`（concat/xfade、amix、独立 srt）、`edit-export.js`（zip + FCPXML/EDL） |

> **结论（已拍板 D13，2026-10-05）**：文本链路走云端**是有意为之**——产品负责人明确"文本可以用云端，不一定非要用本地；特殊场景可以接着用本地模型"。`prd.md` §1 已按此修正为：**图像/视频/音频与私有素材不出本机；文本链路可用云端 LLM，本地模型作为离线/隐私/降本场景的备选**。因此 §3 的 C1 从"矛盾"转为"已决策"。**仍需注意**：文档里其它写"全内网/数据不出机器"的地方要按此口径逐个对齐（见 P8）。

## 5. 建议：四页唯一职责 + 工作流分层 + 本地/外部判据

### 5.1 四页的"唯一职责"（建议稿，供拍板）

| 页面 | **唯一职责**（一句话） | 明确不做 |
| --- | --- | --- |
| **项目工作区** | **一部剧的主线**：按阶段推进、看产物、做人工拍板（定妆确认/风险提示/成片） | 不做自由画布、不做单张试模型 |
| **画布** | **临时编辑表面**：自由排版、局部试作、与 Agent 协作；事实以项目为准，画布可丢弃 | **不拥有任何生产事实**（不持有剧本/任务唯一状态） |
| **生图工作台** | **单张试验台**：试模型、试提示词、批量出图、归档 | 不推进项目阶段、不做分镜/关键帧编排 |
| **生视频工作台** | **单段试验台**：试视频模型与参数 | 同上；不做片段编排与成片 |
| **影视流水线** | **跑批控制台**：起 run、续跑、并发/历史/成本 | 不做内容编辑；阶段推进以项目页为主入口 |

> 关键取舍：**画布与工作台都是"试验/编辑表面"，生产事实只有一处（Project + run）**。这能一次性解决 C2 与 C3。
>
> ✅ **P9 已拍板（D14，2026-10-05）：画布要接入服务端事实链**——产品负责人明确"关系重大"，并希望借外部更高维度评审再定集成深度。三种接入深度见 **§5.5**。

### 5.5 画布接入服务端事实链：三种深度（**给外部评审的核心议题**）

现状（C7）：画布产物不进 `Artifact/AssetRef`、`CanvasProject` 无 `projectId`、`Project.canvasIds` 无写入方、画布生成走浏览器直连、画布资产与服务端资产双轨。

| 方案 | 做什么 | 得到什么 | 代价 / 风险 | 我的倾向 |
| --- | --- | --- | --- | --- |
| **A 最小接入** | ① 画布产物生成后登记进服务端 `Artifact`（可选再登记 `AssetRef`）② `CanvasProject` 增 `projectId`，`Project.canvasIds` 补写入方 | 画布产物可被 `/assets`、`/tasks`、资料包看到；画布与项目可互相跳转 | 画布生成仍在浏览器直连：无进度、刷新即丢、与工作台/流水线三套语义（C10 未解） | 可作为**第一步**（改动小、可逆） |
| **B 中度接入（推荐）** | A + ③ 画布生成改走服务端队列（与工作台同一条 `/api/images/enqueue` / `/api/generate/video`） | 画布获得进度/恢复/归档；**三套提交链收敛成一条**；Agent 通过画布生成的产物天然进事实链 | 需要画布生成链改造（前端调用点 + 模板/参数映射）；离线能力下降（依赖网关可达） | ✅ **推荐**：一次解决 C7 + C10 |
| **C 重度接入** | B + ④ 画布**节点图本身**由服务端持有（画布成为项目事实的一部分，多设备一致） | 真正的"服务端唯一事实"，多端协作基础 | 与 D7"画布单写者/不做自动合并"冲突；与"画布是可替换编辑表面"（DP:462）定位冲突；改动最大、回归面最广 | ❌ 不建议在本期做 |

**给外部评审的三个问题**：
1. 画布在你们的产品语义里，应该是**"临时草稿纸"**（A/B 足够）还是**"项目事实的一部分"**（必须 C）？如果是前者，是否需要为此在设计上明确"画布产物默认不入档、需一键提升为资产"的交互？
2. 若选 B，**画布离线可用性**下降是否可接受？（现在画布生成不依赖网关，改后依赖）
3. A/B/C 之外，是否存在**第四条路**：让"资料包导出"只依赖服务端事实，而画布只提供"把本地草稿提升为服务端资产"的一个显式动作？（即把集成点收缩成一个用户动作，而不是全链路打通）

### 5.2 "工作流"分层（见 §2.3）——建议立即统一文案：**阶段 / 跑批 / 模板 / 画布**。

### 5.3 判据：什么时候才允许走外部 API（建议稿）

1. **本地没有该能力**（例：视频超分、大参数视频模型）或**本地显存不够**（16GB 硬顶）→ 才考虑外部；
2. **本地有但质量不达标** → 只在"有可复算的质量对比"时才转外部（不能凭感觉）；
3. **数据边界**：走外部 = 数据离开本机。**图像/视频/音频素材默认不出本机**（这也是 HANDOFF 的既有硬约束）；**文本是否可出本机必须显式拍板**（当前事实上已出）；
4. **外部必须是显式开关**，默认关、失败不静默回落（沿用现有 RunningHub 语义）。

### 5.4 对"现阶段要不要接外部 API"的建议

- **不新增外部 API 投入**：RunningHub 保持"默认关、不投入"（Key 已失效、未真机验证）；浏览器直连第三方渠道**保留但收窄**（见 §6 的 P6）。
- **但必须拍板一件事**：文本上云（C1）。两条路各有代价——
  - **承认文本可上云**：改动最小，但要改 PRD 的"数据不出本机"叙事；
  - **切回本地 Ollama**：`config.pipeline.llmModel` 指向本地模型即可，代价是 **14.45 t/s**、32k 上下文，长篇分卷/分集阶段会显著变慢、且与 ComfyUI 争 16GB 显存（numCtx=32768 实测占 14.9GB）。

## 附录 A：给外部评审的自包含简报（可直接整段粘贴给 GPT）

### A.1 这是什么

一个**本地化 AI 短剧生产平台**（私有部署，面向海外发行）。技术形态：零依赖 Node 网关（`canvas-server`）+ React 前端（画布/工作台/项目工作区）+ 内网 ComfyUI（出图/出视频）+ 云端 LLM（写剧本/分镜/提示词改写）。当前规模：网关 ~19,500 行、测试 ~955 项、ComfyUI 模板 19 个。
