# 子 agent 任务与验收清单

> 借鉴来源：`github/spec-kit` v1.1.0 —— 见 `spec-kit-adoption-plan.md` §2 A2。
> 它有一句判据值得原样引用：
> **"A contribution is evaluated on the evidence it carries, not on how plausible its reasoning sounds."**
> （一份产出的分量取决于它携带的证据，而不是它的推理听起来多合理。）
>
> 本文件同时约束**派活方**（我）与**接活方**（子 agent）。

## 一、派活时必须写清（任务书七件）

1. **背景与目标** —— 为什么要做、做完是什么样（一句话能验收的形态）。
2. **边界** —— ① 可以改/新增哪些文件；② **绝对不能碰**哪些文件；③ 点名工作区里哪些改动是
   **别人正在改的在制品**（只读、不许回滚、不许当自己的）。
3. **验收标准** —— 必须贴**哪些证据**（不能只写"完成"）。
4. **环境事实** —— 测试命令与**当前基线通过数**、服务端口、能否重启、可用的只读接口。
5. **复用线索** —— 仓库里已有的同类实现（避免重造）。
6. **用户偏好约束** —— 例如禁解释性小字、预览必须站内、禁硬编码等。
7. **禁止事项** —— 不许 `git add/commit`、不许重启生产服务、不许引新依赖等。

## 二、接活方必须交出的证据（八条）

| # | 要求 | 说明 |
|---|---|---|
| 1 | **正例 + 反例测试各 ≥1** | 每个行为变更都要有；只写"正常路径通过"不算 |
| 2 | **bug 修复给"改前失败 → 改后通过"对比** | 必须是**真实命令输出**，不是描述；没有"改前失败"证据的不算修复 |
| 3 | **无法自动化的路径要说明限制** | 并给可复现的手工步骤，不要含糊带过 |
| 4 | **禁止用"理论上会…/应该能…"代替证据** | 未实测的结论必须标注"未验证" |
| 5 | **外部副作用给可验证句柄** | 上传/发布/写远端/改生产数据 → 给 URL / ID / 绝对路径 / 文件行号，供派活方复核 |
| 6 | **真实数据干跑** | 用项目里的**真实对象**跑一遍并贴真实输出；**只用夹具/自造数据不算** |
| 7 | **`git diff --stat` + 每个 hunk 一句话** | 让人不看 diff 也能判断改动面 |
| 8 | **声明未触碰禁忌文件** | 并指出工作区里哪些改动**不是自己的**（多 agent 并行时必须） |

## 三、派活方必须做的复核（不认自报）

- **自己跑一遍测试**，不看对方贴的结果。
- **自己走一次真实路径**：调接口 / CDP 真实点击 UI。（**API 路径 ≠ UI 路径**，用 API 跑的不算数。）
- **对账对方的"未触碰 X"声明**（`git status` 逐个文件比对）。
- **产物要落到真实位置**：`run` 侧有产物 ≠ `项目` 侧有；接口返回 ≠ 页面渲染出。
- **自己错了要认**：若复核发现"失败"其实是复核方自己用错参数，必须**明确更正记录**，
  不能把锅记在下游头上（已发生过，记在 `pilot-issues.md`）。

## 四、反向清单（以下都**不算**证据）

- "已完成 / 已修复 / 已测试通过"的**自述**（无论措辞多肯定）。
- 只贴测试文件名、不贴结果的。
- 用夹具数据代替真实项目数据的"端到端验证"。
- 拿**相邻产物的结论**当自己的一手证据（下结论前先抓一手证据）。
- 改前没有失败证据的"bug 修复"。
- **append 型日志里的历史报错**被当成当前 bug 证据（先确认对应代码还在不在）。

## 五、并行派活纪律

- **一任务一关注点**；按**文件边界**切分，同一个热点文件只允许一个任务独占（串行派）。
- **在途任务设上限**；超限时停在当前边界并报告，不要继续开新面。
- 子 agent 之间**不许**改对方正在改的文件；发现重叠立即停手上报。
