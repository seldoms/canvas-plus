# 以项目为中心的产品骨架梳理（2026-10-07）

> 背景：导航条上 项目 / 画布 / 流水线 / AI图片 / AI视频 五个入口目前**数据层有链、体验层并列**。
> 目标形态：**以项目为中心，但不绑死项目**——五个入口都能独立用，一旦产物归因到项目就自动被项目"看见"。

## 1. 一句话主线

```
新建项目 → 自动进入画布拆解（剧本/设定铺成节点）→ 画布产出资料包（角色/场景/道具）
        → 生图生视频带着项目归因发生 → 流水线按集消费资料包逐镜生产 → 合成成片
```

不绑死项目的含义：

- 画布可以没有项目，随便画；
- 生图/生视频工作台可以没有项目，随便生成；
- 流水线必须从项目的剧本版本（sourceRevision）启动——这是唯一的硬绑定，也是合理的。

**粘合剂是"归因"而不是"入口"**：每个生成任务的 meta（`projectId / episodeId / sceneId / shotId`）决定了产物事后能被哪个项目看见。入口不需要串，数据自己会串。

## 2. 现状盘点（事实，非设想）

| 层 | 已有 | 出处 |
|---|---|---|
| 项目对象 | `canvasIds[] / runIds[] / assetRefs[] / plan / script / sourceRevisionId` 一根主干 | `canvas-server/src/projects.js` |
| 任务归因 | `job.meta: {runId, stageId, itemId, projectId, episodeId, sceneId, shotId}` 全量可选透传 | 网关 domain-contract §3.10 |
| 画布→项目 | M2 事实链：画布节点可绑定项目事实；项目能列出关联画布 | M2 已验收 |
| 工作台→项目 | M3 互通：工作台产物可 `registerAssetRef` 进项目 | M3 已验收 |
| 流水线 | 七段（剧本→分镜→服化道→定妆→关键帧→配音→成片）真实闭环已通 | M6 已验收（20.25s 成片） |
| Agent | 53 工具：画布 25 + 工作台/素材 7 + 项目流水线 19 + 站点 2，三层视角齐 | 2026-10-08 更新 |

## 3. 断点清单（"没有机结合"的具体位置）

1. **B1 入口并列、无引导**：建完项目后系统不告诉你下一步该去哪。用户要自己背"先去画布拆，再去流水线跑"这条隐性流程。
2. **B2 项目→画布不自动**：建项目不会自动建拆解画布。剧本/人物/场景还停在 JSON 里，没有"铺到画布上变成可编辑节点"的脚手架动作。
3. **B3 资料包不是一等公民**：角色包/场景包/道具包目前散在 assetRefs 里，没有"这个项目的资料包"聚合视图，也没有"资料包 → 定妆/服化道阶段直接消费"的显式通道（定妆照项目沉淀的"一个 job 一个主体一个视角"铁律还没产品化）。
4. **B4 归因不可见**：生图/生视频任务虽然能带 projectId/shotId，但工作台 UI 上没有"归属到项目/镜头"的选择器，归因靠流水线内部写，用户手工作品回不去项目。
5. **B5 流水线↔画布双向不通**：分镜镜头不能"发到画布"做视觉排布，画布上的调整也不能回写镜头（patchShot 只有 API，没有画布入口）。
6. **B6 插件分发是上游**：Agent 面板"安装插件"引导指向官方 `@basketikun/canvas-agent`，工友装到的是没有 53 工具、没有 pipeline 技能的旧版（详见 §5）。

## 4. 目标形态：一条主线，三种进入方式

```
                    ┌─────────────────── 项目（主干）───────────────────┐
                    │  剧本版本 · 风格锚点 · 资料包 · 集/场/镜 · run 记录 │
                    └───────▲───────────▲───────────▲───────────▲──────┘
                            │           │           │           │
        ① 从项目出发         │ 建画布     │ 产物回挂   │ 选包开跑   │ 逐集调整
   （引导式：建项目→拆解画布） │           │           │           │
                            │           │           │           │
        ② 从画布出发    画布（拆解/排布/灵感）          │           │
   （自由画，事后"认领"到项目）────────────────────────┘           │
                            │                                    │
        ③ 从生成出发    生图/生视频工作台（带归因选择器）─────────────┘
   （自由生成，选"归入项目/镜头"）
```

- **项目是索引，不是容器**：不复制产物，只存引用（assetRefs/canvasIds/runIds）。删除项目不删画布和素材。
- **流水线页是"按集展开的生产台"**：左栏选集，七段面板逐镜调整——这已是现状，保持。
- **画布是"项目的空间视图"**：剧本拆解、资料排布、分镜预览都在这里发生；画布改动通过既有 M2 事实链回写项目。

## 5. 插件分发：我们的改动怎么送达工友

现状：面板"安装插件"引导 = 上游官方 npm 包（`@basketikun/canvas-agent@latest`）+ 官方 marketplace。我们的 53 工具、pipeline 技能、中文 instructions **只存在于服务器本地 fork**。

| 路径 | 做法 | 成本 | 适用 |
|---|---|---|---|
| **A. 站点内置 Agent**（已是我们的构建） | 工友直接用网页侧边栏 Agent——服务器 `canvas-agent.service` 跑的就是我们的 dist，53 工具天然生效，**无需安装任何东西** | 0 | 所有工友的日常使用 ✅ 主推荐 |
| **B. 内部 marketplace** | `codex plugin marketplace add /sobey/canvas-plus`（或挂内网 git 地址让工友 add URL）→ 装到的插件含 pipeline 技能与新引导 | 低：把仓库推到一个工友可访问的 git 地址 | 想在 Codex app/CLI 里用的人 |
| **C. 私有 npm** | 起 Verdaccio，发 `@sobey/canvas-agent`，引导文案换成内网包名 | 中：多一个服务要养 | 长期、多人、多机 |
| **D. 手动 MCP** | `codex mcp add infinite-canvas -- node <服务器>/canvas-agent/dist/index.js mcp` | 0 但不可复制 | 临时调试 |

配套动作（无论选哪条）：

1. 改 `agent-connect-view` 的引导文案（i18n：`agent.connect.plugin*`），把"官方插件/npx 官方包"换成内网说明——否则 UI 永远把人引到旧版；
2. 插件 `plugin.json` 的 name/version 与上游区分开（如 `canvas-plus`，version 独立递增），避免工友机器上官方插件和内网插件互相覆盖。

## 6. 分阶段落地建议

- **P0 串联引导（纯前端，1 步先见效）**
  - 项目页加"下一步"引导卡：建项目 →「创建拆解画布」按钮（调 M2 接口把剧本/人物/场景铺成节点）→「进入流水线」；
  - 改 Agent 安装引导文案（§5 配套 1）。
- **P1 资料包一等公民**
  - 项目下聚合视图：角色包/场景包/道具包（读 assetRefs 分组渲染）；
  - 工作台/画布生成时可选"归入项目资料包"（写 assetRefs + job.meta）——把"一个 job 一个主体一个视角"做成资料包的生成模板；
  - 定妆/服化道阶段从资料包显式取料（现在靠编译链隐式引用，做成可见的"选用"动作）。
- **P2 画布↔流水线双向**
  - 分镜镜头"发到画布"排布，画布调整回写 patchShot；
  - 归因选择器进生图/生视频工作台（B4）。
- **P3 分发私有化**：内部 marketplace（B 路径）跑通，写进工友 onboarding 一页纸。

## 7. 风险与注意

- 项目只存引用：任何"归入项目"都不能复制实体，否则会出现两份真相；
- run 与集的关联还欠着（清单 #1）：P1 做资料包时一并定义 run↔episode 的归属写法；
- 引导不能挡自由路径：三个入口独立可用的行为一个都不许改坏（不绑死项目的底线）。
